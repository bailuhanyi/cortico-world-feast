# 食时 · cortico-world-feast

先给她一天，再给她一桌饭。

> **只想学会怎么用？** 看 [`GUIDE.md`](GUIDE.md)：三分钟上手、四个面板怎么点、一起吃饭怎么玩、36 项配置（分 5 张卡）、常见情况。
> 这一份 README 讲的是"里面有什么、为什么这么做"。

0.7.0 起她有自己的日子：每晚到点请她自己写明天怎么过，第二天按它过；主人能在「今天」面板看此刻她在哪儿、临时改掉某一段。下面「[她的一天](#她的一天)」一节讲这个。

桌上是 800 道菜（28 个菜系组），每道都有九维口味分值、上桌的样子、香气、口感、余韵，和一段 40-400 字的实吃描写。她能自己按菜系挑着吃，主人也能从面板把一道菜端到她面前，或者整桌端过去；还能**和她一起吃一顿**——邀请她、互相喂一口，你吃了什么她也知道。**同一道菜每次吃到的都不一样**——温度、状态、配的那口都会变，所以连着吃三次不会说三遍同一句话。吃过什么、对什么反应、攒出来的口味画像跨天留着。饭点提醒默认开着，可以在配置里一键关掉。

## 里面有什么

**菜品库**：800 道，28 个菜系组。中餐 13 组 468 道、外餐 14 组 331 道，外加白米饭一道（单独归在「白饭」）。

| 中餐（13 组 468 道） | 外餐（14 组 331 道） |
| --- | --- |
| 川菜、粤菜、江浙沪菜、北方菜、湘菜、西南菜、东北菜、西北菜、闽台菜、鲁菜、鄂菜、徽菜、赣菜、白饭（只有白米饭 1 道） | 日料、韩式、东南亚、南亚菜、墨西哥菜、拉美菜、意菜、法餐、南欧菜、中欧菜、东欧菜、英美菜、中东菜、非洲菜 |

**菜系和形态是两根轴，不混在一起。** `cuisine` 只说这道菜**从哪来**（川菜、法餐、中东菜…），`category` 只说它**是什么形态**（热菜、凉菜、主食、汤羹、面点、小吃、甜品、饮品、烧烤、火锅）。0.2.0 之前这两根轴是混着的——同一道菜可能既算「中式小吃」又算「江浙菜」，生煎包和小笼包就这么被拆到了两组。0.4.0 又把两根轴上残留的两个「例外组」清了：**家常菜**（风格，不是地域）和**甜品**（`category` 里已经有同名值）。所以现在一道菜只有一个菜系归属，想按形态找就筛 `category`——「甜品」是筛 `category` 得到的，不是筛 `cuisine`。

**唯一的例外是白米饭。** 它没有产地可写（写哪个省都是编的），所以单独放在 `src/data/staples.json`，`cuisine` 记「白饭」——**不叫「主食」**：那是 `category` 上的形态名，菜系里再用一次就是同一根轴出现两次（卡片会印出「主食·主食」，两个下拉各有一项同名）。全库就这一道。和拆掉的「甜品」「家常菜」不同：那两个是风格/形态，会越收越多；这个上限被 `GROUP_CAPS` 和一条守门测试钉死在 1，加第二道直接报错（DISH-SPEC 第 2.1 节写了理由）。

每道菜 15 个字段：`id` / `name` / `alias` / `cuisine` / `category` / `region` / `ingredients` / `method` / `serving` / `taste`（九维）/ `texture` / `aroma` / `finish` / `prose` / `keywords`。

九维是 **辣 麻 咸 鲜 甜 酸 苦 油 香**，0-100 的整数，按菜的真实口味给：麻婆豆腐的麻在 80 以上，清蒸鱼辣不过 10，糖醋排骨甜在 60-80。这些分值不是装饰——她在面板和工具回执里看到的条、算出来的口味画像，都是从这个数上来的。

**四个面板**（Coo 世界页签里）+ 一条挂在菜单面板顶部的「一起吃饭」条

- **菜单**：左边筛、右边看。筛选是**先选类别、再挑菜系**——选了「汤羹」，菜系下拉就只列汤羹里真有的那几个，不会给你一个按下去必然为空的选项；换类别时对不上的菜系会自动清掉。点一道菜能翻到九维口味条、食材、做法、上桌的样子和整段实吃描写；按钮「端给她」就把这道菜放到她面前。端过来的那道会出现在顶上一条等待条里，右边写着**还剩多久**（每 30 秒自己走一格，到点收走）。菜单面板最顶上还有**一起吃饭那条**（见下面那一节）。
- **套餐**：一桌一桌地端。上面是 8 套内置套餐（四菜一汤、一桌酒席、一个人吃、清爽一餐、按她的口味配、川菜一桌、粤菜一桌、夜宵），每张卡带「看这一桌」——预设是**按槽位现配的**，端之前得看得见具体是哪几道，而且**卡上列的这几道就是端过去的那几道**（预览和端用同一颗种子）。下面是攒新的一桌：勾菜、起名字、存下来，下次直接端；勾好了不存也能直接端。整桌端过去之后，等待条会写着还剩几道，`feast_eat` 不带参数就是吃桌上还没吃的那道。
- **吃过什么**：吃过多少回、今天几回、尝过几道、口味画像（九维均值 + 一句句读出来的判断）、吃得最多的几道、最近几口（主人喂的那一口会单独标出来）、她自己记过的反应。
- **今天**：她自己写下的这一天。顶部一条「此刻」（现在几点、落在哪一段），下面是今天和明天的时间线——**此刻那一段点亮、过去的压暗**；再往下是「请她写明天」按钮、临时改主意表单，和最近 30 天的往期（点一天展开全天）。详情见下一节。

## 一桌菜是怎么配出来的

一张桌有两种定义，按**为什么这么定**分开：

- **固定桌** `dishes: [id…]`——就是那几道。你在面板上勾出来的桌用这种，勾了哪几道就是哪几道。
- **配方桌** `slots: [槽…]`——按槽位现配。8 套内置预设全是这种。

预设**一律不写死 dish id**。写死 5 个 id 的话，库一改名预设就悄悄指向不存在的菜；配方桌加了新菜自动受益。代价是"某个槽位在库里凑不出数"只会在真端上桌时才暴露，所以有一条守门测试钉着：**每个预设的每个槽位，现在就必须配得齐**。

**按口味配菜不是"取最相近的 N 道"。** 画像偏辣时的正确结果不是"5 道辣菜"，而是"辣的 2 道热菜 + 1 道解辣的凉菜 + 1 道汤"——**结构由槽位保证，槽内才按味道距离挑**。槽内也不直接取前 N 名，而是从前 3×N 名里按种子抽，否则每次配出来一模一样，而且几道菜会挤在同一个味道上。

一桌的口味签名是九维平均，但**饮品不算进去**——一杯奶茶的油咸辣天然接近 0，算进去会把「烧烤 + 蚕豆泥 + 奶茶」平均成「清爽」，那就成了假话。

自定义的桌单独存 `feast/combos.json`，不进 `state.json`：它是**你写的内容**，不是"她吃过什么"的记录，所以点「清空吃过的记录」不会把它一起删掉。

## 一起吃饭

前面那些都是"她吃"。这一块是两个**一起吃一顿**：有开始、有散桌。

菜单面板最顶上那条就是它。三种样子：

- **没在吃**：只有一个「🍽 一起吃」按钮。按下去就是**你邀请她**，她会收到一条 `feast.together`（`origin: internal`）问你一起吃点。
- **她说想和你一起吃饭（还剩 N 分钟）**：这是**她主动开口**。她那边没有向你发消息的通道，所以她的邀请只是挂在面板上等你回应 + 她自己会跟你说一句；你说「好，一起吃」这顿就开席。这种邀请**一天最多两次**、挂 **20 分钟**没人应就自己收掉——不催、不重发。
- **正一起吃**：上面写着起头的是谁、多少分钟了，下面能看到你都在吃什么、喂了她几口、她分了你哪一口（带「接过来 / 下次吧」），还有「散桌」。

**喂一口**：在菜单里翻到一道菜、点开详情，按「我也吃这道」是**你自己**也在吃它；面板上那条会话条里可以填一句「我在吃…」（比如"在啃面包"）。

三条账分得很清楚，别混：

| 这件事 | 记在哪 | 为什么 |
| --- | --- | --- |
| 你喂她一口 | 进 `eaten`（标成"主人喂的一口"）+ `counts` | 吃进嘴里的就是吃过的；进 `counts` 之后「同一道第二口」的说法自然和第一口不一样 |
| 她回喂你一口 | 只记一条 gesture（喂了什么、你接没接） | 那是**你**吃的。进 `eaten` 会让"她吃过什么"说谎 |
| 你自己吃什么 | 只记在**这一顿**里 | 同上：`eaten` 是她的账，不是两个人的账 |

**一口不等于一道**：喂一口**不消耗桌上的菜**，它只是"这一顿她尝过这道"。所以喂到第几口、还剩几道，两个数不会互相打架。

**说你吃什么时别编**：从库里点一道，她会看到菜名和菜系；写一句（"在啃面包"）时，**那一句会先当菜名精确查一次库**——正好是库里某道菜的名字（或 id / 别名）就按那道记，不是菜名才当自由文本，并在事件正文里写明"这条没进库，只按他说的这句写"。两步都不许拿库里别的菜替你形容（自由文本**不做模糊匹配**：写"面包"不会命中"番茄蒜香烤面包"）。

**这顿怎么算完**：她的那份吃完、你说散桌、或者挂太久（默认 60 分钟）——三者任一成立就收摊；收摊后面板上还留一句"刚才那顿：…"。会话说到底也是**短命的**，跟"端来的菜"一样住在 `state.json` 里。

## 她的一天

前面那些都是"吃"。这一块是**她怎么过日子**。

在 0.7.0 之前，她在食时里只有一个时间维度：饭点。剩下的时间是空白的——你问她「你这会儿在干嘛」，她只能按常理推断；晚上十点说「早点睡」，她没有任何可参照的东西。

### 一晚一次，她自己写明天

到点（`lifeGenerateAt`，默认 22:00）推一条 `feast.life.plan`，正文里给出：

- 明天的日期和**日型**（上班日 / 休息日 / 外出日 / 宅家日 / 加班日 / 摸鱼日，按工作日周末加权挑，也可以在配置里固定一种）
- 最近三天的流水（做过什么，让她有连续感）
- 饭点（别把吃饭那两段排成别的事）
- 格式要求：从 00:00 排到 24:00、不重叠不留空档，每段 `{ start, end, activity, location, detail }`，想写穿了什么、手边有什么可以加 `outfit` / `props`

**用 `feast_life_plan` 交回**，World 用 `normalizePlan` 校验（至少两段、每段要有 `activity`）、补空档、去重叠，落盘。**她没写就模板兜底**，第二天总归有内容。

**零 API Key。** World 契约不允许直接读 Memory、也不允许调 Persona 的工具，`host.cognition?` 也不保证存在——所以这里**不内置任何模型调用**。用的是她已经配好的那个模型，她的人设由 Coo 自带，不读 `AGENT.md`。

**不重复叫她**：推之前先落一个 `pending` 占位（`items` 为空——补了空档的话看起来就像她已经想好了）。重启、tick 重入都不会重复叫同一天；主人也能在面板上手动按「请她写明天」再叫一次。

### 「此刻在做什么」为什么分三层

Cortico 的 `envPromptVars()` **只在前缀重建时重算**，不是每轮请求。把「此刻」放进去，她会一整天以为自己还在早上那件事里。

所以拆成三层，各管各的时机：

| 层 | 载体 | 变多快 | 管什么 |
| --- | --- | --- | --- |
| **低频** | `{{feast_life_block}}`（进系统前缀） | 一天一两次 | 今天是什么日子、全天打算、**傍晚之后**附上明天的 |
| **中频** | `feast.life.moment` 事件 | 换一件事才一次 | 时段切换时搭车推一句「这会儿在…」 |
| **按需** | `feast_life_now` 工具 | 她自己问 | 精确到半小时的「此刻」+ 待会儿想做的 + 今天早些时候 |

时段事件走 `debounce` 投递（不打断她），**睡觉时段不推**，同一段里不重复推。饭点事件的正文也顺带一句「你这会儿本来在…」，把两条线缝上。

**工具回执里不重复前缀的内容。** `feast_life_now` 只讲事实（现在几点、在哪段、待会儿、早些时候），**不附**「怎么把这些带进聊天」「正事优先」「工具用法」——那三段已经在系统前缀里了，回执再贴一遍纯属重复。这一条把回执从 508 token 压到 **86**（约省 83%），有测试钉着（`nowText 不重复系统前缀里已有的说话方式`）。

### 会花多少 token / 上下文

实测（按 `publish-check` 同一套估算口径：中日文 0.6、其他 0.3）：

**常驻（每轮都在的系统提示，不随轮数累积）**

| 项 | token |
| --- | --- |
| 工具定义 16 个 | 2634 |
| `ENV_PROMPT.md` | 538 |
| 系统前缀 `{{feast_life_block}}` | 537（早晨）/ 570（傍晚含明天） |

其中 0.7.0 新增约 **+1800**（7 个 `feast_life_*` 工具 +1265、系统前缀 +537~570）。前缀被设计成一天变一两次，所以**大概率命中前缀缓存**，不是每轮全价。

**一次性（事件 / 回执，进对话历史）**

| 项 | 单条 | 频次 | 一天 |
| --- | --- | --- | --- |
| 写明天 | 258 | 1 | 258 |
| 自由时间 | 194 | 3 | 582 |
| 时段事件 | 44 | 换事才推，约 6 | 264 |
| `feast_life_now` | 86 | 按需 | — |
| `feast_life_view` | 122 | 按需 | — |

**一天约 1100 token**（含她各查一次约 1300），一周约 7700–9200。

想更省：`lifeFreeSlots: ''` 砍掉一天 582、`lifeMomentEvents: false` 砍掉 264、`lifeEnabled: false` 让系统前缀归零（工具定义那 1265 还在）。**不建议**去压工具定义的 schema 说明——`feast_life_plan` 的 442 token 是逐字段格式要求，压了她更容易交回错格式。

### 她自己的时间

日程说的是「打算」，这一块说的是「真的去做了」。原来那个独立的**自由时间**扩展（`cortico-world-playtime`）已经并进来了。

到点（默认 **10:00 / 14:00 / 21:00**）推一条 `feast.life.free`：告诉她现在是她自己的时间，给一份**例子**，想做什么就做什么，做完随手 `feast_life_play` 记一笔。没记就催一次，催完放掉。

**`lifeFreeGoal` 是「叫醒的上限」，不是任务额度。** 这几条要说清楚，否则读起来就变成派活：

- **记到几件就不再按点叫**——只表示「今天不再按时叫你了」，**不表示不许再动**。
- 到了、甚至过了这个数，照样能记、照样算数（`recordPlay` 根本不看 `goal`）。
- **想开始随时能开始**：`feast_life_start` 就是不给等叫醒的入口，跳过今天之后也能用。
- 例子之外的事、临时起意的、什么也没做只是发呆，**全都算**。不记也不影响她继续做事。

**只在日程说是自由段时才叫。** 这是合并后最关键的一条：日程说她这会儿在上班、通勤、被占着，就**不叫**——否则会出现「现在是你自己的时间」和「你在上班」互相打脸。睡觉时段同样不叫。判断看活动名（「自己的时间 / 在家玩 / 休息 / 玩 / 摸鱼」这类算自由）。

叫醒事件里会带上日程的那一段，把两条线缝上：

> 【食时 · 你自己的时间 · 21:00】现在是你自己的时间，不是主人找你，也不是待办。
> 你现在在家，随便做点什么都行。
> 今天已经玩过：还没。
> 想做的话，下面这些只是个例子，不照着也行；想到什么就做什么，什么都不做也可以：
> - 出去转转，走一小段路，看看外面现在什么样
> ...
> 做完随手用 `feast_life_play` 记一笔……不记也没关系，记只是给你自己攒。

**菜单是可配置文本，默认只给通用说法。** 不点名任何别的扩展的工具——World 契约不允许一个 World 依赖另一个扩展，认证也查这条。想让她真用上某个工具（花语乡、B 站、空间动态…），自己在 `lifeFreeMenu` 里写明：

```
- 去花语乡转转（bloom_inbox peek 看 town/lounge）
- 发一条空间动态（qq_qzone action=post）
```

**记账单独存一份** `<数据目录>/feast/life/play-YYYY-MM-DD.json`，不写进日程：`feast_life_plan` 会整个重写一天，记进去她下次交回就覆盖了。计划和事实的生命周期不同，就该分开存。

「今天」面板底下那块「她自己的时间」显示今天记了几件、下一档几点、她做了什么；到数了标一句「不再按点叫（想动随时动）」。**被日程挡掉的那一档也会写出来**（`21:00 · 没叫：她那会儿在加班赶工`）——0.7.1 这里是纯静默，面板上只剩「今天没有了」，很容易以为功能坏了。

判据是**排除法**：只排除明确被占用的（睡、回笼觉、午睡、上班、通勤、开会、加班、居家办公…），其余一律算她的空档。0.7.1 用的是白名单（`自己的时间|自由|在家玩|休息|摸鱼|追剧…`），实测在真实日程的 13 段里只命中 2 段、默认三档里两档被静默跳过——白名单判反了会互相打脸（上班时说「这是你的时间」），但把「她分明闲着」漏掉一样是错，所以折中成排除法。

睡觉的判据也收成了一处（`isAsleepActivity`）：以前各处都写 `/睡/`，认不出「回笼觉」「打盹」「补觉」，那一档会把她从回笼觉里叫起来。

### 她当天可以改主意

日程不是刻在石头上的，`feast_life_adjust` 给她三条路：

| 想做的 | 怎么做 |
| --- | --- |
| 改成别的 | `start` / `end` + `activity`，原来压在这段上的安排被截断或拆开 |
| **不做了** | `activity` **留空**。挖出来的洞归**后面那一段**（「算了不去了，直接开始下一件」） |
| 取消开头那一截 | 同上，会补一段中性的「在家」，不会变成凌晨起床 |

**为什么洞归后一段**：归前一段的话，取消「出门散步」会把「吃午饭」拉成三个小时——那是在撒谎。

**过去改不了**：今天已经过完的时段她不能回头改。日程是**计划**，过去应该是**事实**，回头篡改就等于在编自己做过什么。她真忘了就用 `feast_life_now` 查。配置项 `lifeAdjustPast`（默认 `false`）可以打开；**主人从面板改不受这个限制**——那是在补记事实，改动署名记成 `owner`。

**改完立刻生效**：缓存马上更新，另外补一条 `feast.life.moment`（`meta.reason: 'adjust'`）。`#lifeMoment` 靠段标识做 debounce，改完那一刻它还停在旧段上——不主动补的话，她下一秒说话的依据还是旧的。只有改到「此刻」那一段才推，改晚上的事不会冒一条。

系统前缀里「今天的打算」那行下面还有一句许可，把这件事说在做决定的时刻：

> 今天的打算：起床洗漱、吃早饭 → 通勤 → 上班 → …
> （这是你早上给自己写的，不是任务，随时可以变——想改成别的就用 `feast_life_adjust` 盖掉那一段，不想做了就把 `activity` 留空，改完直接说决定本身。）

### 今天面板

- **顶部一条「此刻」**：现在几点、落在哪一段（`约 19:30，在吃晚饭（家）`），睡着时说「她睡着了」。
- **今天 / 明天的时间线**：每段写时间、在做什么（带地点）、以及她写的细节 / 穿着 / 手边的东西 / 和谁在一起。**此刻那一段用强调色点亮，过去那些压暗**。**饭点挂在对应的那一段上**（`饭点 18:00`），**吃过的那一档打勾**；**点任意一行**，起止和活动名自动填进「临时改主意」。
- **请她写明天**：跟着明天的状态走——没写 = 「请她写明天」；等她写 = 灰掉的「已经跟她说了…」；**她已经写好 = 「请她重新想想」+ 二次确认**。见下面那张表。
- **临时改主意**：填一段时间 + 一件事，盖上原来那段（原来的会被截断或拆开）。**「做什么」留空 = 不做了**。改动记进 `changes`，时间线上标出来。**已经过去的时间从面板改不了吗？**——面板这条路是放行的（主人是在补记事实），她的工具那条路锁着。
- **往期**：最近 30 天，点一天展开全天。

「请她写明天」为什么要有状态：

| 明天的状态 | 按钮 | 按了会怎样 |
| --- | --- | --- |
| 还没写 | 「请她写明天」 | 落占位 + 推一条请她写的消息 |
| 她在写、还没交回 | 「已经跟她说了…」（灰的） | 不重复催，也不重写占位 |
| **她已经写好了** | 「请她重新想想」 | 先问你一句；**只推邀请、不落盘**——她真交回了才盖掉旧版，不理会就原样留着 |

0.7.1 在这里是无条件 `pendingDay()` 覆盖：点一下就把她**已经写好**的明天清成「等她写」的空壳（实测 `source: coo`、3 段 → 点一下 → `source: pending`、0 段）。连点三下还会推三条 `feast.life.plan` 事件。

面板**不复用** `momentLine()`——那是给模型看的事件正文，末尾带着「不用特意跟主人汇报」，显示给主人就是一句写给 AI 的话。服务端 `list` 因此返回结构化数据（`nowItem` / `nowMinute` / `nowHm` / `mealSlots` / `eatenToday`），句由面板自己拼。

### 生图工作室联动（0.7.1）

和生图工作室（`cortico-world-imggen`）各跑各的，不调对方工具（World 契约不允许），只靠两件事：

1. **共享素材库的文件约定**：双方都读 `<数据目录>/imggen-library/`，feast 扫每个条目的 `entry.json`，拿到人物、衣柜、场景、道具和穿搭习惯。带 mtime 缓存（没变就不重扫）；目录自动跟 imggen 的 `libraryRoot`（读不到再降级默认路径，`lifeWardrobeDir` 可手动覆盖，配置页上有原生选目录按钮）。
2. **提示词里各写一句指向对方**：feast 在 `{{feast_life_block}}` 加一句「想发图时穿着地点按日程来」，imggen 在他们的 ENV_PROMPT 加反向一句。

**自动补 outfit** 的优先级（模型没填时才补）：

```
① 模型自己填的（能对上库就归一成正名，对不上保留原词）
② 情境穿搭 outfitByContext（她显式配的「睡前→睡衣」习惯）
③ 情境默认（内置常识表，库里 find 到才用）
④ 延续上一段（睡觉那段不延续、不硬猜）
⑤ 场景默认（场景条目的 defaultOutfit）
⑥ 她的 defaultOutfit（人物条目里的，最后兜底）
```

**情境穿搭排在延续前面**：situation 是她自己写的强信号。起床段 carry 睡衣对，但上班段 carry 成睡衣就荒谬。

**读不到就静默降级**：目录不存在、坏 JSON、散图条目、四类全空——一律返回空库，联动那部分省掉，绝不抛错（抛错会把整个 World 卸载），也绝不影响她的一天。库不存在那个 outfit **保留原词**，交给 imggen 的 `findEntries` 做包含匹配。

每段补完会留一个 `outfitSource`（`model` / `context` / `situation-default` / `carry` / `scene` / `default`），落盘也留着——0.7.2 补的，以前 `cleanItem` 不认这个字段，标完一落盘就没了，排错时分不清「她写的」和「自动补的」。

### 界限

- `scene` / `outfit` / `props` 是**日程里的文本字段**，0.7.1 起会跟生图工作室的素材库联动：库里有正名就归一、模型没填 `outfit` 时按习惯补（见「[生图工作室联动](#生图工作室联动0-7-1)」）。库读不到就退回纯文本，不做库里没有的校验。
- 日程存 `<数据目录>/feast/life/YYYY-MM-DD.json`，一天一个文件，`tmp → rename` 原子写（断电不会留半个 JSON）。
- **清「吃过的记录」不动日程，清「她的一天」也不动 `state.json` / `combos.json`**——存储页因此是三项。
- 关掉 `lifeEnabled` 时，`envPromptVars()` 返回 `{ feast_life_block: '' }` 而**不是 `null`**：`null` 会把整份 `ENV_PROMPT`（连饭点说明）一起省略。
- 这个方法**永不抛错**（契约里抛错会把整个 World 卸载），全程 `try/catch` 兜住。

---

`feast_eat` 的回执不是把档案贴一遍。它分两层：

**事实层**（每次一样）：上桌的样子、香气、口感、余韵、整段 `prose`。这是这道菜的底。

**当下层**（每次不同）：温度怎么变的、这一回该说哪个角度（第一回的"第一印象"、第二回的"吃了一半怎么变"、第三回起的"熟客例行"）、吃的时候什么状态、配了什么、吃到一半有什么变化。用 `${dish.id}|${第几次}|${日期}` 做种子，所以同一道菜连着吃两次读起来不一样，而同一个「第几次 + 同一天」重放是稳定的（测试锁住了这一条）。

角度是按次数**硬绑**的，不是从一个大池子里随机抽——随机抽的话第二回仍可能落到第一回那套话上。三档各自 7-8 句，同一天连吃两回也不会挑到同一句。

不合口味的时候（`dislikeChance` 掷中）会另起一句，并且指出**这道菜自己最强的那个维度**顶住了她——麻婆豆腐是「麻起来之后什么都尝不出来」，不是随便套一句「太咸」。

## 饭点提醒

默认 **11:30 和 18:00** 各一顿，可以在配置里改时间、加档位、或者整个关掉。

- 到点推一条 `feast.meal` 事件（`origin: internal`，是她自己的饭点，不是主人发的消息）
- 正文写今天吃过什么 + 三道候选，让她自己挑
- 没吃就催一次（默认 40 分钟后），催完就放掉，不刷屏
- 她说 `feast_skip` 就今天不再叫
- 应用 15:00 才打开这种：一天一档都没叫过的话，补最近过去的那一顿，不让一整天白过
- 上一顿挂太久（2 小时）就放掉，但**同一拍还会看下一档**——午饭没吃不该把晚饭一起吞掉

配置项（`worlds.feast.*`，全是热改）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 世界总开关（install.ps1 会设成 true） |
| `mealReminder` | `true` | **饭点提醒开关**。关掉就完全不叫，菜单和工具都还在 |
| `mealSlots` | `11:30,18:00` | 饭点档位，逗号分隔（中文逗号也认） |
| `mealGraceMin` | `20` | 超过多少分钟就不算「到点」了 |
| `mealRetryMin` | `40` | 没吃的话隔多久催一次 |
| `mealMaxRetries` | `1` | 最多催几回（0 = 只叫一次） |
| `tickSec` | `30` | 多久看一次表 |
| `askReaction` | `true` | 回执里是否提醒她记一句反应 |
| `dislikeChance` | `0` | 吃到不对付的概率（%） |
| `avoidRepeat` | `true` | 随机挑菜时避开上一次那道 |
| `ownerFeedTTL` | `30` | 主人端来的菜（或一桌）几分钟后收走 |
| `comboSize` | `4` | 没指定套餐时，「来一桌」配几道 |
| `togetherInviteMin` | `20` | 她挂着的那条「想和你一起吃」留多久 |
| `togetherMaxInvites` | `2` | 她自己一天最多主动邀请几次（0 = 不主动邀请） |
| `togetherTTLMin` | `60` | 一顿「一起吃饭」最多挂多久，到点自动散桌 |
| `menuSize` | `5` | 每次随机给几道 |
| `lifeEnabled` | `true` | **「她的一天」总开关**。关掉后不生成日程、不往系统提示里放她的日子、不推时段事件；饭点照旧 |
| `lifeGenerateAt` | `22:00` | 每晚几点请她自己写明天 |
| `lifePrecision` | `halfhour` | 「此刻」精确到哪一档：`minute` / `halfhour` / `block`。只影响工具和事件，**不进系统前缀** |
| `lifeUpcoming` | `3` | 「她待会儿想做」最多列几件 |
| `lifeTomorrowAfter` | `18:00` | 过了这个点，系统前缀里附上明天的打算（一天只变一次，不打穿前缀缓存） |
| `lifeMomentEvents` | `true` | 时段切换时搭车推一句（debounce、睡觉不推） |
| `lifeDayType` | 空 | 固定日型：留空按工作日/周末加权挑；填 `workday` / `restday` / `outing` / `homebody` / `overtime` / `slacking` 就固定用它 |
| `lifeVoiceOn` | `true` | 附上「怎么把这些带进聊天」那段说话方式 |
| `lifeMaxItems` | `24` | 她自己写明天时段数上限，写多了按时间顺序裁掉后面的 |
| `lifeAdjustPast` | `false` | 允许她改今天已经过完的时段（默认关：那是事实，不是计划。主人从面板改不受限制） |
| `lifeFreeSlots` | `10:00,14:00,21:00` | 她自己的时间：几点叫醒她。留空 = 不叫（工具和面板照样能用） |
| `lifeFreeGoal` | `3` | 每天想玩几件；做满不再叫。0 = 只叫不计数 |
| `lifeFreeGraceMin` | `20` | 档位容错：到点后多少分钟内还算这一档 |
| `lifeFreeRetryMin` | `40` | 没记就催：隔多少分钟再催 |
| `lifeFreeMaxRetries` | `1` | 一档最多催几次；0 = 不催 |
| `lifeFreeMenu` | 4 条通用说法 | 叫醒时贴给她的菜单。**默认不点名任何别的扩展的工具**；要用具体工具自己填 |
| `lifeFreeAskReport` | `true` | 做完要不要提醒她跟主人说一句 |

端来的那道**剩多久是看得见的**：`feast.feed` 的气泡写清到几点为止（"11:35 端的 → 12:05 之前吃掉都算数"），吃的时候回执里也补一句还剩多少，菜单面板的等待条右边有一行自己会走的倒计时。端一整桌时（`feast.table`）等待条改写成「还剩 3 / 5 道」并列出还没吃的那几道。一起吃饭那条通道是 `feast.together`，`meta.kind` 分清是哪件事（邀请 / 喂一口 / 你自己在吃什么 / 回应她的回喂 / 散桌）。她的日子走 `feast.life.plan`（每晚请她写明天）和 `feast.life.moment`（换一件事时搭的短事件）。


测试用的是 `test/harness.mjs` 里那个十几行的小骨架，不用 `node --test`——受限沙箱里它要 spawn 子进程会被 EPERM 挡住。

`dist/webui.js` 只在 Coo 里跑，测试里跑不到，是最容易藏错误的地方，所以 `panels.test.mjs` 用几十行 DOM 桩把四个面板真挂一遍：点卡片进详情、点「端给她」调 `feed`、勾几道端一桌调 `serve`、筛选与搜索带条件、失败时出错误卡、今天面板点亮此刻那一段并调 `adjust`。**面板 id 不写死**——测试拿 `webUi().panels` 声明的 id 去对账客户端导出的那几个（声明了 4 个就要求导出 4 个）。少了不会报错，只会在宿主里点进去是一片空白。

每个用例给一个**独立的 `dataDir`**（带上 pid 和启动时间）。共用同一个目录的话，上一个用例端过的菜、吃过的记录会漏到下一个用例里，"刚端上来"和"早就吃完了"混在一起，测出来的东西是假的。

面板测试里不要拿 `await new Promise((r) => setTimeout(r, 0))` 当同步用——一次点击要跨好几轮 microtask 和 timer，固定次数是竞态（机器快就过、慢就挂，我们踩过一次）。等结果出现，用 `waitFor(() => 条件, '在等什么')`。

`waitFor` 用 `performance.now()` 计时、不用 `Date.now()`：面板的倒计时会被测试换成假钟，用被换掉的那个钟计时就永远等不到超时。假钟本身也要**从 `{ now }` 对象上现读**，别把时间冻结成一个常数——冻结了的话，把钟拨走它也不知道。

状态落在 `<dataDir>/feast/state.json`。跨天只清饭点那一层（`fired` / `pending` / `skippedDay`），`eaten` / `reactions` / `counts` / `together` 留着——她不会因为过了零点就忘了自己爱吃麻婆豆腐，也不会忘了昨天你们一起吃过一顿。自定义套餐在 `<dataDir>/feast/combos.json`，那是你写的内容。她的日子在 `<dataDir>/feast/life/YYYY-MM-DD.json`，**三份互不牵连**（清任何一份都不动另外两份）。

加菜之前先读 `DISH-SPEC.md`：15 个字段怎么写、九维怎么给（按真实口味，不凑数）、套话黑名单、每栏的字数区间。一条硬规矩是**同一组里 8 段实吃描写的开头不许用同一个句式**——单看一条都合格，8 条摆在一起就成了模子。

## 设计上刻意没做的

- **`envPromptVars()` 只放低频的东西**。`{{feast_life_block}}` 里只有一天变一两次的内容（今天什么日子、全天打算、傍晚后的明天），**不放「此刻」**——它只在前缀重建时重算，放进去会滞后几小时，还会每换一件事就重算一次前缀。精确状态走 `feast_life_now` 工具和 `feast.life.moment` 事件。吃过什么也同理，要用 `feast_history` 查，不往提示词里塞。
- **工具描述写得窄**。它们每一次都在前缀里，占的是长久的便宜或长久的债。
- **没有「每日目标」**。不像 `playtime`，这里没有配额，只有 `mealMaxRetries` 给催饭封顶——吃饭不该变成 KPI。
- **细节描写不重复**。库里没有任何「令人回味无穷」「唇齿留香」这类套话；`validate-dishes.mjs` 会把它们当成问题报出来。
- **没有"她给主人发消息"的通道**。宿主只有主人 → 她这一个方向，所以她的邀请只能"挂一条等你回应 + 她自己说出口"，不假装能主动推给你。同理，你那半边的营养和口味画像也不做——自由文本没有九维，编不如不写。
